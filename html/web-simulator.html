Simulatore attacchi web

Cinque vulnerabilità web classiche spiegate in quattro fasi: contesto, bug, effetto, difesa. Scegli un attacco, cambia l'input e guarda nel log cosa farebbe un server vulnerabile.

  • 5 attacchi OWASP
  • 4 fasi ciascuno
  • Livello intermedio
  • 25–35 minuti
  • Tutto nel tuo browser
A chi serve, prerequisiti e obiettivi
A chi serve
Chi sviluppa applicazioni web e chi inizia con la sicurezza offensiva in ottica difensiva.
Prerequisiti
Basi di HTTP, HTML e SQL; nozione di cosa sia un cookie di sessione.

Obiettivi di apprendimento

  • Riconoscere dove nasce ciascuna vulnerabilità nel codice e nel flusso di una richiesta.
  • Valutare l'impatto reale di ogni attacco, senza sopravvalutarlo né sottovalutarlo.
  • Associare a ogni classe la difesa corretta e verificabile.

Nessuna richiesta di rete, nessun database reale, nessun comando eseguito. Tecniche mostrate solo a fini di studio e di difesa: usale esclusivamente su sistemi tuoi o con autorizzazione scritta. Per scenari guidati in un terminale apri il Lab virtuale.

    Console — SQL Injection (simulata)

    Prova con admin oppure incolla admin' OR '1'='1 nel campo utente. Il log descrive cosa farebbe il server vulnerabile.

    [PRONTO] Ambiente didattico — nessun database reale coinvolto
    [INFO] Premi il pulsante: le quattro fasi qui sopra si accendono una alla volta
    Impatto tipico: critico
    Percorso didattico

    Fase 1 — Cosa fa l'applicazione

    Il form di login invia nome e password al backend. Il backend costruisce una stringa SQL e la manda al database per chiedere: «esiste questa coppia?».

    Fase 2 — Dove nasce il bug

    Il programmatore concatena il testo del form direttamente nella query. Il database riceve un'unica stringa e non può più distinguere i comandi SQL dai dati.

    "SELECT * FROM users WHERE user='" + input + "' AND pass='" + password + "'"

    Fase 3 — Cosa fa l'input malevolo

    Chiudendo la stringa con un apice e aggiungendo OR '1'='1, la condizione diventa sempre vera: il login può riuscire senza conoscere la password reale.

    admin' OR '1'='1' --

    Fase 4 — Cosa fa il difensore

    • Query parametrizzate (prepared statement): il database tratta l'input solo come dato, mai come comando.
    • Account del database con privilegi minimi (niente DROP, niente lettura di file).
    • Validazione di lunghezza e formato; messaggi d'errore generici.
    • Log delle query anomale; un WAF solo come strato aggiuntivo, mai come difesa principale.
    Console — XSS (simulata)

    Inserisci un commento normale o prova <script>alert(1)</script>. Nessuno script viene eseguito: il log descrive soltanto il flusso.

    [PRONTO] XSS seguito dalla pubblicazione del commento alla sua visualizzazione
    Impatto tipico: alto
    Percorso didattico

    Fase 1 — Superficie di attacco

    Ogni dato controllabile dall'utente che finisce in una pagina: commenti, biografie del profilo, parametri dell'URL riflessi nella risposta o letti dal JavaScript.

    Fase 2 — Dove nasce il bug

    L'input non viene codificato in output. Può succedere sul server, quando il template stampa il testo senza escape, oppure nel browser, quando il JavaScript lo inserisce come HTML (per esempio con innerHTML) anziché come testo: in entrambi i casi i tag al suo interno diventano codice.

    element.innerHTML = comment; // usa textContent

    Fase 3 — Tre varianti

    Si distinguono per dove viene conservato il payload e per chi lo inserisce nella pagina:

    • Memorizzato (stored): il payload è salvato sul server (un commento) e colpisce chiunque apra la pagina.
    • Riflesso (reflected): il server rimanda il payload nella risposta a chi segue un link preparato, una volta sola.
    • Basato sul DOM: il payload non passa dal server; è il JavaScript della pagina a inserire input (per esempio da URL) nel DOM.

    Fase 4 — Effetto e difesa

    Il codice gira nel browser della vittima: furto del cookie di sessione, azioni a nome della vittima, redirect, falsi form di login.

    <img src=x onerror="/* codice JS */">
    • Codifica in output (trattare < come testo), textContent al posto di innerHTML.
    • Content-Security-Policy per limitare l'esecuzione di script non autorizzati.
    • Cookie di sessione con flag HttpOnly e SameSite.
    Console — Brute Force (simulata)

    La wordlist sotto è solo didattica. La simulazione mostra tentativi e risposte HTTP fittizie, non invia richieste a login reali.

    [PRONTO] Ciclo tentativo/risposta simulato in locale
    Impatto tipico: alto
    Percorso didattico

    Fase 1 — Cosa prova l'attaccante

    Invia in automatico richieste di login usando liste di password comuni: raccolte da violazioni passate (come RockYou) e varianti prevedibili (nome dell'azienda + anno, stagione + punto esclamativo).

    Fase 2 — Perché a volte funziona

    Password scelte da persone, quindi prevedibili, e nessun limite ai tentativi: per l'attaccante il costo diventa basso.

    Fase 3 — Segnale di successo

    Una risposta diversa dalle altre (200 invece di 401), un cookie di sessione, un redirect alla dashboard: il simulatore li descrive nel log.

    Fase 4 — Difesa

    • Rate limiting per IP e per account; CAPTCHA progressivo.
    • Secondo fattore (TOTP, WebAuthn): la sola password indovinata non basta più.
    • Allarmi sui picchi di accessi falliti; rifiutare le password presenti negli elenchi di credenziali compromesse (per esempio Have I Been Pwned).
    Console — Upload non sicuro (simulata)

    Esempio didattico: file foto.jpg che in realtà contiene codice server. Nessun file viene caricato sul disco.

    [PRONTO] Validazione file spiegata passo-passo
    Impatto tipico: critico
    Percorso didattico

    Fase 1 — Funzione legittima

    L'utente carica un'immagine o un PDF; il server la memorizza e mostra un link pubblico.

    Fase 2 — Controllo insufficiente

    Si controlla solo l'estensione o il tipo MIME dichiarato dal client: entrambi falsificabili.

    Fase 3 — Escalation

    Se la cartella /uploads esegue PHP o script, aprire l'URL del file può eseguire comandi sul server.

    Fase 4 — Difesa

    • Elenco di estensioni consentite e verifica dei magic bytes reali del contenuto.
    • Salvataggio fuori dalla web root o in uno storage che non esegue codice; file serviti con Content-Disposition: attachment.
    • Nome casuale (UUID), scansione antivirus, limiti di dimensione.
    Console — CSRF (simulata)

    Domini fittizi (bank.example.com). Il log mostra come il browser allega da solo il cookie di sessione a una richiesta che non hai deciso tu.

    [PRONTO] Nessuna richiesta di rete verso domini reali
    Impatto tipico: alto
    Percorso didattico

    Fase 1 — Sessione valida

    Hai fatto login su bank.example.com; il browser conserva un cookie di sessione.

    Fase 2 — Trappola cross-site

    Apri un'altra pagina che contiene un form o un'immagine diretti a un URL sensibile della banca.

    Fase 3 — Richiesta «automatica»

    Il browser allega i cookie: per il server sembra una tua azione, anche se non hai confermato nulla.

    <form action="https://bank.example.com/transfer" method="POST">...</form>

    Fase 4 — Difesa

    • Token CSRF univoco per sessione e per form.
    • Cookie SameSite=Lax o Strict; verifica dell'header Origin.
    • Conferma esplicita (password, 2FA) per operazioni irreversibili.
